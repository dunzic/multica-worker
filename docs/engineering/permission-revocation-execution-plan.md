# 权限撤销与任务内嵌附件链接执行计划

更新日期：2026-10-15。

目标是让成员被移出工作区或群组后，既有实时连接和已经取得的站内附件下载链接不能继续获得新的受保护内容。覆盖任务（Issue）正文、评论、回复、群组消息，以及从这些位置复制出去的站内文件链接；保留正常成员的文件预览、下载和智能体协作能力。

当前状态：本轮服务端及网页／桌面的权限适配、自测、独立初审和修复复审已完成，可以进入受控平台验收。R1 跨工作区及话题任务消息泄漏已技术关闭，R3 整域 CDN 凭证持续签发已完成应用代码级复审；移动端 R2 尚未修复，按用户确定的范围保留为发布阻断项。最终五包回归通过，但仍有环境跳过、已确认基线失败，以及清理用例曾失败后转绿的可重复性风险。实际证据见[开发验证记录](permission-revocation-verification.md)，结论和代码指纹见[独立架构评审](permission-revocation-architecture-review.md)。当前不能据此发布生产后端。

2026-10-15 范围决定：用户明确选择本轮仅完成服务端和网页／桌面，移动端认证预览与点击下载不纳入实现。此决定不是接受旧移动端失效的风险，也不关闭兼容问题；未来发布前须完成客户端适配、版本协调及独立移动端回归。

后续 Git 交付已获用户授权：提交本轮改动、合并至 `main`，并推送到自有仓库 `dunzic/multica-worker`。实现提交为 `e869e6197a5824fb8e47af67f79fefae0cc4fc48`，与独立复审代码快照一致。此授权不包含发布标签、生产部署或安装包发布，也不关闭移动端兼容阻断。

## 一 本轮范围与权限规则

### 必须覆盖的范围

1. 工作区移除成员或成员主动退出后，关闭该成员在该工作区的既有实时连接，停止后续受保护消息投递。
2. 已取得的短期附件能力链接，在实际读取文件时重新校验权限，不能仅凭签名仍在有效期内就继续放行。
3. 群组附件除工作区成员资格外，还要求当前有效的群组参与资格。只移出群组、仍保留工作区身份，也必须撤销该群组文件的后续访问。
4. 正文、评论、回复、附件卡片及直接打开链接使用一致的服务端规则；预览、原文件下载和分段请求均纳入检查。
5. 文件权限由文件记录所属工作区和群组决定。将链接贴入另一个任务或群组，不自动授予目标位置的读者源文件权限。
6. 用户定向投递可能跨工作区；每帧必须按来源工作区和群组重新授权，不能只检查连接当前所在的工作区。仅有话题 ID 的任务派发及生命周期消息须反查话题所属群组；话题、群组和工作区不能错误配对。失权来源的消息丢弃，其他仍有效工作区的连接保持可用。
7. 登录、显式会话刷新、滑动续期及 CDN 中间件均停止签发整域文件访问 cookie。清除浏览器 cookie 不等于撤销已复制的凭证，历史凭证仍有独立上线门槛。

### 不改变的产品边界

- 本轮不新增独立的任务负责人、任务参与者或项目级文件权限模型。普通任务继续遵循现有工作区访问模型；不能将其描述成已具备独立任务级访问控制。
- 外部网盘、第三方网站和公开文件地址的访问权限由来源服务控制。禁止把外部链接自动改写成站内链接，也不通过代理下载替用户绕过来源权限。
- 已经下载到设备、进入浏览器缓存或已经进入传输过程的内容不能被远程收回。验收重点是撤权后的新授权检查、新请求和后续发送批次；不承诺追回已交付字节。
- 本轮不吸收其他社区功能，不调整文件数量限制，不更改 CLI 名称、服务默认地址、发行渠道或群组业务模型。

### 链接分类与目标行为

| 链接或入口 | 目标权限规则 | 必须说明的边界 |
| --- | --- | --- |
| 站内稳定附件链接，包括任务正文、评论和回复中的链接 | 根据附件记录解析源工作区，检查当前成员及群组权限后读取 | 不信任当前页面工作区、请求参数或引用位置来扩大权限 |
| 为原生下载生成的短期能力链接 | 签名绑定附件、授权主体、有效期和用途；每次兑换重新查当前权限 | 它仍是持有即可兑换的短期凭证，不等于证明兑换者就是原申请人 |
| 已签发的存储服务或 CDN 直链 | 先盘点生成入口、有效期及缓存行为，再决定受保护场景如何避免绕过应用授权 | 仅修复下载按钮，不代表全部预览直链都能即时撤销 |
| 外部或公开链接 | 保持外部链接语义，由来源服务授权 | 站内成员移除不会使第三方链接自动失效 |

短期能力链接的原生客户端用途必须在设计评审中明确确认：允许当前有权限的主体生成临时、可转交的链接，但该主体失去权限后旧链接不得继续兑换。若业务要求"仅原申请人本人可用"，需要另行设计兑换者认证，不能把签名中的用户标识当作已经满足这一要求。

## 四 执行顺序

### 第一阶段 固定基线和建立失败证据

1. 核对当前分支、完整提交号、未提交文件和候选来源。保留已产生的实现草稿，不将其误当成干净基线；保留用户缓存、安装包和既有测试证据。
2. 使用只含原始基线代码的独立快照，加入能暴露缺陷的最小回归用例。分别证明"移除后旧实时连接仍有机会收到消息"和"移除后旧能力链接仍可兑换"；记录实际断言失败，不把环境启动失败算成缺陷复现。
3. 使用仓库管理的隔离数据库，按仓库迁移流程初始化。禁止复用默认或生产库，不修改共享数据库账号或重建共享容器。日志只记录库用途和检查结果，不记录连接密码。
4. 使用仓库要求的 Go 版本和默认测试 CLI 防护脚本。测试进程打印"数据库不可达而跳过"时视为未执行，不接受退出码为零作为通过证据。默认测试不调用用户安装的智能体 CLI；真实智能体冒烟测试须另外明确授权。

阶段出口：原始基线上的失败断言及修复分支上的同一用例均可重复运行。

### 第二阶段 适配实时连接权限回收

1. 成员移除或主动退出事务成功后，再触发该工作区、该成员的连接清理；事务失败不能提前断开有效用户。
2. 冻结有界发送批次后，使用最新成员关系重新授权。批量查询必须匹配工作区、用户及适用的群组，不能拼成扩大授权的交叉集合，也不能借用连接工作区授权其他来源的内容。私密消息缺少来源时拒绝；自己的移除通知仅保留界面清理所需标识，禁止夹带正文。
3. 清理连接订阅和待发送队列；跨实例通知丢失、延迟或队列拥塞时，发送前检查仍能阻止失权成员获得后续消息。重新加入后到达的旧移除通知不能误踢新有效身份。
4. 查询超时、失败和过载时不放行受保护数据。限制并发、批次和等待时间，避免单个工作区拖住实时中心。
5. 保留本仓库的群组参与者定向投递与持久化中继；不能因为通过工作区检查，就向全部工作区成员广播群组消息。

阶段出口：真实 WebSocket 与隔离数据库回归通过，同时记录并发、延迟和故障注入结果。

### 第三阶段 适配附件链接及任务引用权限

1. 签名覆盖附件、申请主体、过期时间和用途。兑换时先验证签名，再按附件实际归属查询最新权限；忽略试图覆盖授权主体或工作区的请求头与参数。
2. 普通人员同时检查当前工作区成员资格和适用的群组参与资格。群组附件被引用到任务正文或评论后，不放宽原权限。
3. 智能体必须保留受信任的运行身份及工作区绑定，不能简单退化成智能体所有者的权限。明确任务令牌撤销、智能体移出群组和所有者仍有权限时的行为；这项是合并前设计检查，不以伪造客户端请求头替代真实身份。
4. 对稳定下载、下载元数据、预览定位及实际文件读取入口核对缓存策略。撤权敏感的路径不能仅凭过时正向成员缓存放行；权限查询失败时拒绝访问。
5. 在本地存储、私有对象存储和 CDN 模式下验证下载能力链接统一经过应用授权并流式返回，保留分段下载能力。受保护的预览直链、稳定链接重定向及旧客户端路径逐一审查，不能遗漏绕回存储直链的入口。
6. 如果仍有存储或 CDN 直链无法达到本轮撤权目标，必须在合并前列明具体场景和最长有效窗口，完成设计取舍；不能仅凭能力链接测试通过就宣布"全部附件权限已收口"。
7. 维持现有 API 响应兼容和预览体验。敏感签名响应禁止共享缓存和来源地址泄露；日志不得输出完整能力链接或文件内容。
8. 停止签发和续签整域 CDN cookie；原名字、Domain 和 Path 的浏览器凭证执行过期清理。验证码登录、Google 登录、显式刷新及独立认证中间件路径保持正常，公开头像只保留经过公开类别检查的单对象签名。
9. 旧移动端直接打开认证附件地址的兼容缺陷保留为发布阻断项。本轮不恢复存储直链、不在广播事件中以其他用户代签，也不擅自扩大移动端实现范围。

阶段出口：任务正文、评论、回复、群组和直接链接场景都满足同一权限矩阵；所有剩余绕行路径有明确处置结论。

### 第四阶段 回归和开发自测

先运行失败回归对应的窄范围测试，再扩展到实时模块、附件模块、群组隐私和身份认证测试。SQL 查询变更后执行 `make sqlc` 并检查生成代码；Go 改动执行格式检查、静态检查和相关竞态检测。若改动共享前端，则补充对应组件测试、API schema 测试和 `pnpm typecheck`。

开发自查重点包括授权主体是否可信、事务提交顺序、过时缓存、重连与重新加入竞态、流式读取、原生下载兼容和撤权后的错误处理。自查不替代下一阶段的独立评审。

阶段出口：适配实现和必需自测完成，实际测试结果、已知问题、验证层级及未覆盖环境已记录，可以交付独立评审。

### 第五阶段 架构师智能体独立代码评审

用户已授权在开发和自测完成后，由一个未参与本轮实现的架构师智能体执行独立 code review。初审、R1／R3 修复复审及最终代码指纹均已交付；移动端兼容保持发布阻断，不因本轮范围缩小而关闭。限定范围技术评审完成不等于下述全平台放行条件全部达到。

1. **启动条件**：第二、三阶段实现完成，第四阶段必需自测通过；代码范围、测试结果和未验证项整理齐全。由本轮执行者在同一开发流程中启动独立子智能体，不需要为了评审先提交或推送代码。
2. **评审输入**：提供本计划、固定基线、两项社区候选及适配差异、最终代码快照和测试证据。当前为未提交开发时，评审必须覆盖相对基线的全部相关修改及新增文件，不能只看已有提交；排除用户缓存、密钥、生产数据和无关改动。
3. **评审范围**：检查权限和身份的信任边界、工作区与群组隔离、任务正文和评论内嵌链接、缓存与签名绕行、事务提交顺序、并发撤权和重新加入、持久化中继、原生客户端兼容，以及数据库负载和故障时的拒绝访问行为。
4. **职责边界**：架构师智能体独立阅读代码和证据，可在专用测试环境进行非破坏性验证；不修改产品实现、不提交、不推送、不部署。其结论不替代人工业务验收或上线批准。
5. **评审交付物**：在 `docs/engineering/permission-revocation-architecture-review.md` 保存评审报告，列明受审基线与快照、范围和实际检查；每个发现包含严重程度、文件及行号、触发条件、影响、证据和修复建议。没有发现问题时也须说明残余风险和测试缺口，不能只写"通过"。
6. **修复与复审**：实现者逐项处理发现，补充失败回归和修复后证据，再交由独立评审者复核修改。报告中为每项保留待处理、已修复待复审、已确认关闭或需人工决策的状态；复审结论必须对应最新代码快照。
7. **放行条件**：无未解决的 P0/P1 问题；任何严重程度的越权、跨工作区泄漏、群组隔离失效或身份绕过均为阻断项。其余发现逐项关闭，或经负责人明确接受并记录风险后，才可进入合并申请；评审通过不自动授权发布。

按 [四方评审策略](../feature-review-strategy.md) 保留产品、测试和上线责任人的审查。架构师智能体只负责独立技术评审，不虚构其他角色的批准。

阶段出口：独立评审报告、问题处理记录和最新快照的复审结论齐全，合并阻断项已关闭。

## 五 回归与验收矩阵

| 场景 | 操作和预期 | 主要证据层 |
| --- | --- | --- |
| 工作区移除 | 用户预先建立多个连接；成功移除后，不再收到后续受保护消息，也不能重连 | 真实 WebSocket 与隔离数据库 |
| 主动退出及事务失败 | 退出成功撤权；注入移除事务失败时，仍有效的身份保持可用 | 数据库集成及故障注入 |
| 其他成员与其他工作区 | 同一用户的其他有效工作区、当前工作区的其他成员不被误断开 | 真实 WebSocket 与数据库 |
| 跨工作区定向内容 | A 的旧消息投递到 B 的有效连接；移出 A、仅移出 A 群组、群组删除及错误工作区配对均不能收到 A 正文，B 仍可用 | 真实 WebSocket 与数据库及独立复现 |

## 六 发布与回退门槛

1. 合并前核对所有权限入口，不仅检查新增能力链接。保留来源、适配说明、失败基线和修复后证据；最终检查冲突标记、未合并文件、意外改动及格式问题。
2. 能力令牌格式变更须制定协调发布顺序，避免旧后端和新后端混合处理时拒绝新链接或继续接受旧权限。拒绝旧短期令牌后，客户端应重新申请新链接；不新增长期双格式兼容通道。
3. 单独处理已经签发的 CDN 或存储链接：记录现有有效期、缓存和能否失效，确定暴露窗口及运维措施。应用更新不能被描述为已使这些链接全部即时作废。
4. 后端变化不自动意味着必须重打包桌面端。先验证已安装 Windows/macOS 客户端的认证、下载和预览；仅当客户端需要代码变更或最低版本升级时，再提出打包和升级方案。
5. 上线前由负责人确认灰度范围、拒绝率与数据库负载观测、异常处置及回退方案。不得把回退到不再校验权限的旧实现当作无风险恢复；必要时停用受影响入口并保持拒绝访问。
6. Git 提交、推送、主线合并、真实服务变更与安装包发布均在各自获得授权后执行。
7. 移动端兼容 R2 未关闭前不能把本轮服务端更新作为可直接发布的版本。须先确定最低支持版本、升级／切换策略并补足真实客户端回归；限定范围技术交付不等于全客户端放行。

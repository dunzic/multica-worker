# 报告反馈使用指南

报告内容和协作反馈分开保存：HTML、Markdown、PDF 等附件负责展示；预览中的"报告反馈"面板负责保存可编辑记录、多人修改和修改历史。HTML 内的复选框、脚本或浏览器本地存储不等于已保存的协作数据。

## 网页和桌面端使用

1. 打开聊天、群组或任务正文、评论中的报告附件预览，点击工具栏的"报告反馈"。
2. 首次使用由报告上传者或工作区 `owner`、`admin` 点击"配置字段"。每份报告配置 1 至 20 个字段，支持文本、数字、日期、是／否、单选、多选。
3. 点击"添加记录"，填写记录名称和字段值。需要关联原材料时，在"原文件附件 ID"中填写真实附件 ID；关联不会扩大原文件的访问权限。
4. 点击"保存"后，其他有权限的成员可以查看、编辑。打开面板期间每 5 秒检查更新；"修改记录"显示修改人、时间和修改前后的值。

20 是每份报告的字段数上限，不是记录数或附件数上限。记录按每页 50 条加载，可以继续加载后续记录。

同一条记录被多人同时修改时，后保存的一方会收到冲突提示，当前输入保留。复制需要保留的内容，取消编辑后重新打开最新记录，核对后再保存；系统不会静默覆盖他人的修改。归档由报告上传者或工作区 `owner`、`admin` 操作，历史仍然保留。

已有记录后，不能删除原字段、改变字段类型、移除原选项或增加必填约束；可以调整显示名称，并新增选填字段、选项。历史报告中的静态勾选不会自动变成已确认的人工反馈。

## 是否需要逐个配置智能体

**原生单聊、群组话题不需要逐个复制通用提示词。** 更新运行时后，新运行会通过公共聊天提示词获得报告反馈规则，不依赖某个智能体的名称或业务岗位。代码入口是 `server/internal/daemon/prompt.go` 的 `buildChatPrompt`；单聊和群组话题都进入该流程。

| 使用场景 | 指引来源与边界 |
| --- | --- |
| 原生单聊、群组话题 | 公共运行时提示词自动提供上传、配置字段、创建初始记录和保存确认规则。 |
| 任务执行与评论触发的运行 | 任务、评论中的报告可由人在预览面板配置和编辑；本次智能体自动初始化只接通原生聊天运行。普通任务运行没有这条上传并初始化的通路，不能只补提示词就宣称已接入。 |
| Slack 等外部渠道 | 不自动宣传网页反馈面板；外部消息本身不是可编辑反馈界面，渠道来源附件也不开放这套写入能力。 |
| 各智能体的业务要求 | 可单独指定字段名称、评价依据和报告结构；不要复制通用存储规则，也不要要求代填人工决定。 |

公共指引在运行时中，不会通过一次 Git 推送自动进入现有服务器或用户电脑。需要更新实际执行任务的运行时及其使用的 `multica` CLI，并让新运行使用新版本。只有服务端更新、运行时仍旧时，智能体不会自动获得这些新指引和命令。

## 给智能体的请求示例

> 请生成一份可预览的质量检查报告，并在附件的"报告反馈"中建立可编辑记录。每个检查项一条记录，字段包括复核结果、跟进日期和复核意见；人工字段先留空。每条记录关联实际使用的原文件。请使用平台提供的反馈接口保存初始记录，并读取确认，不要用 HTML 勾选框或 localStorage 代替保存。不要修改已有人工反馈；权限不足或命令不可用时，明确说明。

智能体使用原生聊天运行的任务凭据，只能为**本次运行自己上传的报告**初始化字段和新增记录，不能修改已有字段配置、覆盖已有记录或归档记录。重试必须沿用相同记录 ID；遇到冲突应读取并核对，不要换一个新 ID 绕过冲突或重复建行。

## CLI 接入

先检查当前执行环境是否包含新命令：

```sh
multica attachment feedback --help
```

上传报告后，使用上传响应中的真实附件 UUID。下面的 `REPORT_ATTACHMENT_UUID` 和 `STABLE_ROW_UUID` 是占位符，需要替换；不要原样执行。

```sh
multica attachment feedback get REPORT_ATTACHMENT_UUID
multica attachment feedback configure REPORT_ATTACHMENT_UUID --file fields.json
multica attachment feedback save REPORT_ATTACHMENT_UUID STABLE_ROW_UUID --file row.json
multica attachment feedback get REPORT_ATTACHMENT_UUID
multica attachment feedback history REPORT_ATTACHMENT_UUID
```

`fields.json` 的首次初始化示例：

```json
{
  "expected_revision": 0,
  "fields": [
    {
      "id": "review_result",
      "label": "复核结果",
      "type": "select",
      "required": false,
      "options": ["通过", "需跟进"]
    },
    {
      "id": "review_notes",
      "label": "复核意见",
      "type": "text",
      "required": false,
      "options": []
    }
  ]
}
```

`row.json` 的新增记录示例：

```json
{
  "expected_revision": 0,
  "schema_revision": 1,
  "label": "检查项 A",
  "source_attachment_id": "",
  "values": {
    "review_result": null,
    "review_notes": null
  }
}
```

`schema_revision` 必须使用配置响应或最近一次读取中的版本，示例 `1` 仅对应首次配置。`expected_revision: 0` 表示新增；人工通过 CLI 更新已有记录时必须使用读取到的当前记录版本。`source_attachment_id` 可留空，或填写有权限关联的原文件 UUID。

读取返回非空 `next_cursor` 时，使用 `get --cursor` 或 `history --cursor` 继续读取。仅凭命令发出、页面显示或 HTML 提示文字不能宣称已保存，须以成功响应和读取结果为准。

## 上线前提和权限边界

- 服务端需应用迁移 `611` 至 `614`，部署匹配的 API 和网页版本；桌面端需包含本次共享预览组件更新。
- 自动生成报告还需更新运行时和 CLI。仓库合并、推送不等于部署、发布安装包或更新现有智能体运行环境。
- 每次读取、保存和查看历史都重新校验报告附件的工作区、群组权限；被移除的成员不能继续操作。原文件预览和下载单独校验权限。
- 报告附件仍使用现有文件存储，反馈保存在数据库，不需要另建公开 HTML 存储目录；HTML 沙箱不直接连接数据库。
- 本次验证覆盖网页与共享桌面代码，不含移动端、原生 Windows／Mac 安装验收或真实模型生成验收。测试范围见[验收记录](report-feedback-acceptance-20261018.json)。

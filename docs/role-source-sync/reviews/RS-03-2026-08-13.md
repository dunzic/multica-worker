# RS-03 strategy and deterministic-plan design review

Feature: Snapshot, diff, approval and atomic apply

Gate: strategy and deterministic-plan design

Date: 2026-08-13

Decision: CONDITIONAL — plan core may merge behind the disabled feature; apply remains unavailable

## Customer problem and measurable outcome

An administrator must see a repeatable explanation of what a selected immutable source version would change before approving it. Reopening the same snapshot pair must produce the same plan digest. A changed or corrupted snapshot/plan must be rejected, removals must never silently delete workspace objects, and scan errors must prevent unsafe materialization without disturbing the last-known-good worker.

## Decision

Use two content identities: `manifest_digest` identifies normalized role intent, while `snapshot_digest` also covers adapter/contract versions, canonical diagnostics and source evidence. Plans compare snapshot identities, flatten normalized objects by stable source identity, and hash each independently. Role-core and child-object changes are separated so one skill edit does not appear as a whole-role rewrite.

The plan contains no actor or timestamp because those would make its digest unstable. Approval and apply records will carry actor/time separately. Target removals are always `archive_candidate`; adoption, ownership and archive decisions must be explicit persisted decisions before apply. A blocked action retains its proposed create/update/unchanged operation for understandable preview.

## Architecture expert review

Score: 2/3

Accepted evidence:

- full snapshot identity includes diagnostics and provenance, not only manifest content;
- manifest, snapshot and plan digests are recomputed before planning/approval use;
- diagnostic and object order are canonicalized;
- nested role objects have stable scoped identities and independent digests;
- plans are bounded to 100,000 normalized actions and manifests have generic nested object/artifact limits;
- removals cannot become direct deletes in the deterministic core;
- generated plans can be revalidated after JSON persistence, including summary and operation semantics;
- source, scan request, snapshot, plan, approval, apply-attempt and audit records are source-neutral and contain no foreign keys;
- raw adapter configuration is absent from control-plane persistence; only an opaque daemon config ID and typed safe summary are stored;
- scans use a durable per-source queue with expiring ownership leases and stale reporter rejection;
- audit events are sequence-allocated under the source lock, hash-chained and committed in the same transaction as registration/queue/claim/report mutations;
- every unique/listing/queue index is built concurrently in a separate migration.

Open objections:

- HTTP/heartbeat wiring and tenant authorization are not implemented, so persistence is not externally reachable;
- current-snapshot compare-and-swap and apply idempotency rows exist at the query/schema level but are not yet composed with materialization;
- conflict inventory, explicit adoption and ownership-mask decisions are not yet inputs to the plan;
- atomic materialization and append-only receipt transaction are not implemented.

## Product expert review

Score: 1/3

Accepted evidence:

- actions distinguish create, update, unchanged, archive candidate and blocked states;
- each action carries a stable object identity, risk, before/after digests and an explanatory reason;
- blocked actions retain the operation the source proposed.

Open objections:

- no customer preview/approval workflow or localized recovery guidance exists;
- raw digests are evidence, not sufficient user-facing change descriptions;
- ownership/adoption/archive choices and affected-running-work preview are missing.

## Test expert review

Score: 2/3

Accepted evidence:

- repeated planning of the same snapshots produces byte-equivalent structures and plan digests;
- role and child changes are separated;
- removals become high-risk archive candidates;
- role-scoped and global diagnostic blockers are covered;
- tampered manifest, snapshot and plan data are rejected;
- unchanged snapshots produce no mutation actions;
- diagnostic ordering does not alter snapshot identity;
- a generic nested manifest bomb is rejected before deep validation.

Open objections:

- transaction failure, audit failure, concurrent apply and retry-after-timeout tests await persistence/apply;
- no large-plan benchmark or allocation profile exists;
- persisted JSON, lease concurrency and migration integration still require live PostgreSQL evidence; the isolated-schema test is checked in but locally skipped because PostgreSQL was not running.

## CEO review

Score: 2/3

Accepted evidence:

- deterministic evidence-backed upgrades and safe removal handling are differentiated enterprise value;
- the logic is source-neutral and reusable by future catalog/Git/archive adapters;
- separating immutable intent from approval metadata supports compliance review at scale.

Open objections:

- there is still no usable end-to-end upgrade;
- time-saved, incident-reduction and support-cost metrics cannot be measured yet;
- the 10,000-user load profile and disaster recovery remain unproven.

## Security, privacy and data-loss blockers

- Apply remains disabled until a single transaction commits domain mutations and the receipt together.
- No plan may be approved from mutable live source data; only persisted snapshot and plan digests are valid inputs.
- Same-name unmanaged objects must remain conflicts until an explicit adoption decision is implemented.
- Archive candidates must preserve last-known-good runtime state until approval policy and dependency checks pass.

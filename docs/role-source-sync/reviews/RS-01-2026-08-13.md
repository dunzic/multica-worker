# RS-01 strategy and design review

Feature: Adapter registry and source registration

Gate: combined strategy and initial design

Date: 2026-08-13

Decision: CONDITIONAL — foundation implementation may continue; no product rollout

## Customer problem and measurable outcome

Customers need to import and continuously manage role catalogs without maintaining a separate Multica fork for every source ecosystem. Success requires a second adapter to use the same scan and snapshot contract with no source-specific database or UI branch.

## Decision

Use a trusted, compile-time Go adapter registry and a strict normalized manifest. Keep AgentWaker as the first adapter. Do not dynamically load source-provided code. Do not permit arbitrary adapter extension maps in snapshots; new normalized fields require contract review and versioning.

Rejected alternatives:

- hard-code AgentWaker types throughout API, protocol, database and UI;
- use browser directory upload as the durable source;
- dynamically load shared libraries or execute validators from a source package;
- store arbitrary adapter JSON and defer validation until apply.

## Architecture expert review

Score: 2/3

Accepted evidence:

- stable adapter kind and contract version validation;
- duplicate registration rejection;
- descriptor captured at registration so a mutable adapter cannot change its negotiated identity later;
- concurrency-safe registry access;
- canonical ordering and SHA-256 manifest digest;
- stable ID, artifact path/digest, environment digest, binding reference, capability profile and permission validation;
- artifact bodies and plaintext secret values are structurally absent from the normalized snapshot.

Open objections:

- registry is not wired into daemon/control-plane composition;
- source configuration redaction interface is not implemented;
- source capability negotiation is not exposed through API;
- schema evolution rules need golden JSON compatibility fixtures.

## Product expert review

Score: 1/3

Accepted evidence:

- adapter capabilities prevent UI from advertising unsupported watch, secret, artifact or provenance behavior;
- architecture preserves one generic source-management journey.

Open objections:

- no administrator-facing source registration, preview or detach flow exists;
- source-managed field ownership is not yet presented in user language;
- error and diagnostic copy has not been reviewed in the four supported locales.

## Test expert review

Score: 2/3

Accepted evidence:

- unit tests cover duplicate/invalid adapters, deterministic ordering/hash, duplicate source IDs, config failure, tenant identity, unsafe artifact traversal, unkeyed secret digests, and invalid bindings;
- package tests pass with the repository CI Go version;
- race-enabled package tests pass.

Open objections:

- no property/fuzz tests for canonicalization and hostile manifests;
- no concurrent register/read stress test yet;
- no cross-adapter conformance suite or API compatibility test;
- full server test suite has not yet been executed for this branch.

## CEO review

Score: 2/3

Accepted evidence:

- a generic adapter boundary protects the role supply-chain differentiation while avoiding permanent AgentWaker-only maintenance;
- the normalized contract creates a future path for Git catalogs, signed role bundles and managed marketplaces;
- the design keeps unsafe dynamic plugins out of the initial commercial risk envelope.

Open objections:

- the second-adapter proof and customer adoption metrics are absent;
- operating cost per scan/source and adapter support policy are unmeasured;
- commercial packaging and responsibility boundaries for third-party adapters are undecided.

## Security, privacy and data-loss blockers

- config redaction and secret-transfer contracts are not implemented;
- no source persistence or authorization exists yet;
- the AgentWaker filesystem adapter must pass the RS-02 threat matrix before any real directory can be registered.
